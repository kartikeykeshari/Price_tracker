# Production deployment checklist

This guide covers the application configuration. Hosting, TLS, database operations, firewall rules, and mail reputation still need to be configured and verified in the deployment environment.

## 1. Configure the server

Create `server/.env` from `server/.env.example` using the deployment's secret manager. Set:

- `NODE_ENV=production`
- `MONGO_URI` to an authenticated MongoDB deployment reachable only from the application.
- `JWT_SECRET` to at least 32 randomly generated bytes. Keep it private; rotating it signs out all users.
- `CLIENT_URL` to the exact HTTPS origin users open in their browser, with no path. Serve the client and API on the same site, preferably through one reverse proxy.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, and `SMTP_PASS`; production startup fails without these settings.
- `PORT` if the host requires a specific listening port.
- `TRUST_PROXY_HOPS` only when behind a known reverse proxy. Set it to the number of trusted proxy hops; leave it at `0` when users connect directly.

Never use `*` for the browser origin. The API sets an HttpOnly, Secure, SameSite session cookie in production, checks browser request origins, and only accepts the configured client origin.

New accounts must verify their email address before signing in. Provide a working verification email path in production. Password reset and account recovery flows are not included in this release; plan a support and recovery process before opening registration to the public.

## 2. Prepare MongoDB

Use a dedicated database user with only the required database permissions, restrict network access to the application, enable encrypted connections where supported, and configure tested backups and retention. Ensure Mongoose indexes are created before opening traffic. Indexes support unique user emails, unique product URLs per user, due-check lookups, and expiry of rate-limit buckets.

Rate limits and scheduled work coordination are stored in MongoDB, so they work across application instances. Scheduler locks expire if a worker stops unexpectedly. Price-drop emails are queued on product documents and retried with backoff; delivery is at least once and may duplicate if the mail provider accepts a message just before a worker stops.

## 3. Build and run

```bash
npm run install:all
npm run build --prefix client
npm run start --prefix server
```

Serve `client/dist` and proxy `/api` to the Node server over HTTPS. Configure the web server with a restrictive Content Security Policy for the static client, HTTPS redirects, TLS renewal, request logging, and suitable connection limits. The Express API sends security headers and limits JSON request bodies to 20 KB.

Run the API under a process supervisor or container orchestrator that restarts failed processes, forwards `SIGTERM`, and exposes `/api/health` for readiness checks. The health endpoint returns an error when MongoDB is disconnected. Monitor API errors, MongoDB capacity, scheduler lag, queued email alerts, and SMTP delivery.

## 4. Network and scraping controls

The scraper accepts only HTTP(S), rejects credentials and nonstandard ports, resolves hostnames before requests, blocks private and reserved destinations, validates each redirect, and checks addresses again at socket resolution. Also restrict outbound traffic at the host or cloud firewall to reduce the impact of parser or network edge cases. Do not expose MongoDB or cloud metadata services to the application network.

Scraping is best-effort. Target sites may block automated requests, change page markup, or require JavaScript. The product CSS selector and parser errors help diagnose pages, but the application does not guarantee price accuracy or alert timing. Follow each site's terms and applicable laws.

## 5. Release tracking

The `v1.0.1` Git tag is the published baseline. Version `1.0.2` adds the protections and operational guidance in [CHANGELOG.md](CHANGELOG.md). Users upgrading from 1.0.1 should sign in again because sessions now use HttpOnly cookies instead of browser local storage.
